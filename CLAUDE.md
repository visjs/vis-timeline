# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

vis-timeline is a browser visualization library that renders two related charts, `Timeline` and `Graph2d`, both built on a shared `Core` base class. It's part of the visjs family (uses sibling packages `vis-data` and `vis-util`).

## Commands

```bash
npm install       # install dependencies (also runs husky install via prepare)
npm run lint      # eslint over lib/ and test/
npm test          # run the mocha test suite (jsdom-based, no browser needed)
npm run test-cov  # test suite with nyc coverage (lcov)
npm run build     # build all distributable bundles (standalone/peer/esnext/legacy) into dist/esnext/peer/standalone + declarations/
npm run watch     # rollup --watch, rebuilds the peer/dist bundle on change
npm run clean     # remove dist/esnext/peer/standalone/styles build output
```

Run a single test file directly with mocha (bypassing the babel-register requirement of `npm test` is not needed, it's baked into the script):

```bash
npx mocha --exit --require vis-dev-utils/babel-register test/TimeStep.test.js
```

Tests live in `test/*.test.js` and use `jsdom`/`jsdom-global` + `canvas-mock.js` to fake a DOM, so they run under Node without a real browser. Snapshot assertions use `snap-shot-it`; snapshots are stored in `__snapshots__/`.

There is no separate typecheck script — `types/*.d.ts` are hand-maintained and copied into `declarations/` as part of `npm run build` (see the `cpy` step in the `build` script).

## Architecture

**Core inheritance**: `lib/timeline/Core.js` implements all the shared chart machinery — DOM scaffolding (panels for left/right/top/bottom/center, shadows, background), the `Range` (pan/zoom state), event wiring via Hammer.js gestures, redraw scheduling, and the options/configurator system. `Timeline` (`lib/timeline/Timeline.js`, ES class extending `Core`) and `Graph2d` (`lib/timeline/Graph2d.js`, a pre-ES6-class constructor function bolted onto `Core.prototype`) both extend it and plug in their own item/data rendering component (`ItemSet` for Timeline, `LineGraph` for Graph2d). When changing shared behavior (panning, zooming, options validation, current-time bar, custom-time bars), the fix almost always belongs in `Core.js`, not in the two subclasses.

**Components** (`lib/timeline/component/`): each is a self-contained visual piece composed by Core/Timeline/Graph2d — `TimeAxis`, `ItemSet`, `LineGraph`, `DataAxis`, `Legend`, `Group`/`BackgroundGroup`/`GraphGroup`, `CurrentTime`, `CustomTime`, `ClusterGenerator`. Item rendering itself is further split under `component/item/` (`Item` base class plus `BoxItem`, `RangeItem`, `PointItem`, `BackgroundItem`, `ClusterItem`), and Graph2d's plot styles live under `component/graph2d_types/` (`line`, `bar`, `points`).

**Shared infra** (`lib/shared/`): `Configurator`/`Validator` implement the runtime options-validation and the optional visual options GUI; `Activator` handles click-to-activate/keyboard-capture behavior; `Popup` is the tooltip/popup widget.

**Options**: each chart's full option schema and the GUI configurator schema live in `optionsTimeline.js` / `optionsGraph2d.js` as separate `allOptions`/`configureOptions` exports, not inline in the class files.

**Entry points / build variants** (`lib/entry-*.js`, `lib/bundle-legacy.js`): the same set of exports (`Timeline`, `Graph2d`, `DataSet`/`DataView`/`Queue` re-exported from `vis-data`, `util`, `DOMutil`) is assembled four ways for four output targets:
- `entry-esnext` — no bundled deps/locales/polyfills, for bundler consumers (peer deps expected)
- `entry-peer` — re-exports esnext; peer deps expected at runtime
- `entry-standalone` — bundles moment locales, Hammer, keycharm, vis-data/vis-util — zero external deps
- `bundle-legacy` — deprecated, kept only for backward compatibility

`rollup.config.js` builds the `dist/` legacy bundle; `rollup.build.js` (via `vis-dev-utils`' `generateRollupConfiguration`) builds the esnext/peer/standalone outputs driven by `package.json`. Don't hand-edit output under `dist/`, `esnext/`, `peer/`, `standalone/`, or `declarations/` — they're generated by `npm run build`.

## Conventions

- `require-jsdoc` and `valid-jsdoc` are enforced by eslint for functions, methods, and classes — new public methods need a JSDoc block (return type required, param/return descriptions not required).
- lint-staged runs `prettier --write` then `eslint --fix` on staged `.js`/`.ts` files via the husky `commit-msg` hook.
- Commit messages are validated against `.commitlintrc.js` (conventional-commits style) — this drives semantic-release versioning, so PR commit messages matter.
- Development happens on `master`; PRs should target `master`.
